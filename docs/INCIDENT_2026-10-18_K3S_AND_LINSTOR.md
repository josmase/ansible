# Incident: Kubernetes API timeouts and LINSTOR storage outage

**Date:** 2026-10-18  
**Status (updated 2026-10-19 17:16 CEST):** All three masters report `Ready`, API `/readyz` passes, and etcd has a leader. Workers 204–206 remain `NotReady`; node119 is `Ready`. The LINSTOR controller is back on node119, `Running` and serving its API; all four satellites still report `Connected=False`, and the Piraeus operator is unavailable. Latest K3s process metrics were about 8.7 GiB RSS / 5.7 GiB heap on 201, 2.8 GiB / 1.2 GiB on 202, and 1.7 GiB / 0.6 GiB on 203. All 46 active LINSTOR-resource watch series remain on 201, which still holds the kube-controller-manager and scheduler leases. Controller restart and placement tests now point away from the LINSTOR controller process itself and toward leader-only Kubernetes resource watches/caches interacting with the large LINSTOR CRD inventory; this is a strong hypothesis, not yet proof of the full memory attribution. Profiling has been done and did not identify a single actionable allocation source. Application and snapshot integrity remain unverified.
**Data handling:** No etcd reset, datastore restore, or persistent-volume deletion was performed. Log files and archived journal entries were cleaned only; DRBD I/O was resumed after confirming all replicas were UpToDate. No data loss was observed, but application-level integrity has not been independently verified.

## Findings

1. **Log growth and disk pressure:** Master 201's root filesystem had previously reached 100% use. Its syslog and rotated syslog files had grown to multiple GiB, and etcd defragmentation failed with `no space left on device`. Log cleanup restored space; the most recent reading on 201 was 9.7 GiB free (56% used). Masters 202 and 203 also had multi-GiB syslog files, which were truncated, and archived journals were vacuumed.
2. **Control-plane instability:** The three masters repeatedly lost etcd peer connectivity during this investigation. Proxmox reboots temporarily brought API endpoints back, and one snapshot showed all seven Kubernetes nodes Ready with fresh leases and all three `/readyz` endpoints returning `ok`. That state did not persist; subsequent etcd readiness and API requests failed again.
3. **LINSTOR/DRBD outage:** The LINSTOR controller had been in `CrashLoopBackOff` with 246 restarts; the LINSTOR CSI controller had 1,447 restarts and multiple containers in `CrashLoopBackOff`. The `linstor-controller` service had no endpoints, and all four `LinstorSatellite` objects reported `Connected=False`. The previous controller log ended with `Database initialization error` (report `6AD519AD-00000-000000`, exit status 20). The available container log did not expose the underlying database error. At 21:56 CEST, the controller container was running, but direct container logs showed it repeatedly failing to retrieve the Kubernetes leader-election lock because etcd requests timed out; the service is still not verified ready.
4. **Worker I/O stalls:** Worker 204 had load average near 193 and high I/O pressure; 200 DRBD kernel threads were in uninterruptible `D` state. A sampled DRBD receiver stack was waiting in `drbd_flush_after_epoch`/`receive_Barrier`, and `dumpe2fs -h /dev/drbd1147` was blocked in `blkdev_fsync`. Worker 206 had load average near 130, 130 `D`-state threads, and high I/O pressure; a sampled thread was waiting in `jbd2` for DRBD volume `drbd1138`. These observations establish blocked DRBD I/O, but do not establish the original cause of the etcd failures.
5. **Workload impact:** The API listed failing or unhealthy pods, including the LINSTOR controller/CSI pods and application pods. A Ready node status alone did not indicate that storage-backed workloads were healthy.
6. **Shared Proxmox storage pressure:** The masters' 24 GiB boot disks reside on LVM storage `Kubernetes` on the same Samsung 990 PRO NVMe. The SSD reported no media/data-integrity errors, and the storage pool was about 87% full. Proxmox samples correlated NVMe saturation (about 98–100%) and 1.6–2.1 GB/s read bursts with individual master QEMU processes. Etcd explicitly logged leaders missing 500 ms heartbeats and attributing the delay to slow disk; API linearizable reads stalled for multiple seconds. The read storm moved between 202 and 203 during startup/catch-up. This is strong evidence of disk-contention contribution, though the guest operation causing repeated large reads is not identified.
7. **Peer TLS diagnosis remains unresolved:** All three `peer-ca.crt` files have the same SHA256 (`6cced225…f648ef49`), and each local `peer-server-client.crt` verifies against that CA. Direct mutual-TLS `openssl s_client` handshakes between 201 and 203 succeeded both ways. Nevertheless, etcd corruption-check requests logged `x509: certificate signed by unknown authority`, and servers logged peer connections rejected as `bad certificate`. The peer leaf certificates have different generation dates (201: Aug 4; 202/203: Jun 5, 2026), but their issuers and CA match. Certificate rotation was not attempted.
8. **Ubuntu MOTD fsck probe on CSI volumes:** On workers204 and 206, the blocked `dumpe2fs` processes had parents running `/usr/lib/update-notifier/update-motd-fsck-at-reboot`, invoked by `/etc/update-motd.d/98-fsck-at-reboot`. That Ubuntu script runs `dumpe2fs` across all mounted ext2/3/4 filesystems, including CSI ext4 mounts backed by DRBD. It repeatedly stalled on `/dev/drbd1147` (PVC `pvc-d7bc9b05-3f0b-4720-82f4-33d493646f42`) on 204 and `/dev/drbd1136` (PVC `pvc-3f238dd2-2f65-4fa9-b0d2-94e74dfdde5b`) on 206. This explains the extra blocked login/fsck probes; it does not explain the user suspension that blocked DRBD I/O. A DRBD-aware MOTD wrapper that skips the probe while any `/dev/drbd*` filesystem is mounted was deployed on workers204–206 and GPU node119. It preserves the standard fsck notice on nodes without DRBD mounts. After the volumes were resumed, D-state threads dropped to zero.
9. **The two user-suspended volumes were stuck during failed CSI snapshots:** On 204, 205, and 206, kernel logs show `susp-io(no -> user)` for the Prowlarr resource at 04:33:54–55 CEST and for Radarr at 04:34:06–07. The LINSTOR CSI driver log at 04:34:06 says the Prowlarr snapshot was registered, then `lvcreate` failed on node205 (and reported a failure on node204) because `VG linstor_vg` metadata was 521,660 bytes, above its maximum of 521,472 bytes. The same request reports I/O suspended on all three replicas. The Radarr snapshot request was cancelled immediately after its replicas were suspended. No matching resume transition for either resource appears before 21:55, when `drbdsetup resume-io` was run on all replicas. This identifies the direct cause of the persistent DRBD stalls: snapshot creation failed after suspension and left the user-suspend state set.
10. **LINSTOR VG metadata is exhausted on all three storage workers:** Current LVM reports show a 1,044,480-byte metadata area with 0 bytes free on 204 and 206, and only 512 bytes free on 205. The VGs contain 1,158–1,179 LVs, including 201–265 snapshot LVs and 746–790 backup LVs. Thin-pool data usage is 70.76% on 204, 77.50% on 205, and 89.79% on 206; thin-pool metadata usage is 5.36%, 5.53%, and 6.20%. The snapshot error is specifically the VG metadata area, not exhaustion of thin-pool metadata. The Flux snapshot reconciler runs hourly, prunes old `VolumeSnapshot` objects, and uses a class with `deletionPolicy: Retain`; retained backend snapshots may therefore outlive the Kubernetes objects. That policy interaction is a likely source of LV accumulation, but the remaining `VolumeSnapshotContent` and LINSTOR snapshot inventory must be compared after API recovery before calling it confirmed. The Ansible role installs the thin-pool autoextend profile on the hosts, but the CSI satellite container on 204 has no `/etc/lvm/profile` directory, matching the missing-profile warnings in the snapshot error. This is a separate autoextend configuration gap; it is not the reported VG metadata write failure.
11. **The etcd failure remains a separate unresolved problem:** At 22:07 CEST, master201 was still retrying linearizable `ReadIndex` calls and starting elections at term 781. TCP sessions to peers on port 2380 existed, but there was no leader. Proxmox RRD showed sustained reads from 202 and 203 (about 150–170 MB/s in recent minute averages, with day peaks around 2.1 and 1.9 GB/s), while 201 was near idle. The IOPS limits are present in the live QEMU command; current host NVMe latency/utilization were low after containment, and no scheduled Proxmox `vzdump` jobs are configured. SSH to 202 and 203 still times out during banner exchange. Their Proxmox configs have no QEMU guest agent or serial device, so the guest processes causing the reads cannot currently be inspected. The read bursts are a plausible contributor to the original quorum loss, but their guest-side source and causal link to etcd timeouts remain unproven.

The DRBD stalls are explained by failed snapshots against an exhausted LINSTOR VG metadata area. Their relationship to the etcd peer timeouts is not proven. Stable etcd quorum, recovery of the LINSTOR controller, and application/snapshot integrity checks remain outstanding.

## Recovery actions taken

- Cleaned oversized syslog files and vacuumed archived systemd journal entries; no application logs or persistent-volume data were deleted.
- Applied the Kubernetes node log-rotation setup on masters 201–203. The change is in commits `4cad743`, `eed12a7`, and `ded72d7`.
- Rebooted master 201 through Proxmox. Graceful reboot of 202 timed out, so it was hard-reset and started again. Graceful reboot of 203 timed out, so it was hard-reset. A later hard reset of 201 restored SSH and briefly restored API readiness. No etcd reset/restore command was run.
- Later, Proxmox root SSH access from the jumphost was used to identify VM 202 as a read-burst source (~1.6–1.75 GB/s). Its graceful shutdown again timed out; only VM 202 was reset. Its QEMU read rate fell to zero, but a similar read burst then moved to VM 203. Proxmox read limits of `iops_rd=2500` were applied to the `scsi0` boot disks of VMs 201, 202, and 203. This reduced the 203 observed read rate from ~1.6 GB/s to ~200 MB/s and NVMe utilization from ~100% to ~28% in one sample. Subsequent samples still showed renewed K3s restarts, loss of etcd leader, and API timeouts, so this is a temporary containment measure rather than recovery.
- Deployed an Ansible-managed wrapper for `/etc/update-motd.d/98-fsck-at-reboot` on storage workers204–206 and GPU node119. The wrapper skips Ubuntu's all-mounted-ext-filesystem scan when DRBD devices are mounted, avoiding repeated `dumpe2fs` probes that can hang in the storage path. This suppresses the secondary MOTD-triggered probes; it does not repair DRBD or restore quorum.
- Used `drbdsetup resume-io` on all three replicas for minors 1147 and 1136 after confirming all replicas were UpToDate, quorum-enabled, connected, with no in-flight or out-of-sync blocks. Follow-up showed both resources resumed and all worker thread-level D-state counts at zero. No repair/resync was triggered.
- A later API snapshot from 201 showed all seven nodes Ready, but LINSTOR controller, affinity controller, CSI controller, and Piraeus operator remained in `CrashLoopBackOff`; all four satellites were `Connected=False`. Controller log retrieval through the Kubernetes API then failed because the node proxy to 192.168.1.119:10250 returned 502. No controller diagnostic helper was deployed, and no LINSTOR/DRBD or etcd data was changed.
- Subsequent API requests from 201 hung with `context deadline exceeded`. A read-only attempt to inspect the LINSTOR controller log volume directly on `.119` was denied by host permissions; its SSH account requires an interactive sudo password. Proxmox serial terminal opens but yields no guest shell. No helper pod could be created while the API was timing out.
- API readiness and all-node Ready status were observed temporarily, but follow-up checks showed renewed etcd readiness failures and API timeouts.

### Assessment and next diagnostic step

The measured difference is in the K3s server process. Concentrated LINSTOR API watches and snapshot-object requests on 202 are one candidate; embedded-etcd peer/catch-up buffers and Go retention after sequential master startup are another (see the research below). The Go/process metrics exposed through the API cover the combined K3s server process and do not isolate the API server from embedded etcd or the other control-plane components. Confidence is moderate for the API activity correlation and low for attributing the multi-GiB retained heap to it. There is no evidence of current host memory pressure or of large application pods consuming the difference.

The next discriminating evidence is a time-bounded before/after sample of the 202 API counters and heap metrics while snapshot reconciliation is quiescent versus active, plus a Go heap profile and request identity/audit data. No profiling or controller changes were made during these measurements. The research below describes a controlled follow-up experiment; Prometheus/SAR limitations and the workers' offline state prevent treating the current samples as a stable baseline.

## 2026-10-19 – research into reducing master memory requirements

The current large VM allocations should be treated as recovery headroom, not a demonstrated steady-state requirement. [K3s resource profiling](https://docs.k3s.io/reference/resource-profiling) measured approximately 1.45–1.61 GB for its tested embedded-etcd server baseline. Those tests used K3s v1.26.5 and a much simpler workload; they do not establish a safe budget for this cluster's LINSTOR database, controllers, and snapshot inventory. Our 203 sample also shows that the combined K3s process can currently remain much smaller than 202, although it carries different traffic and started last.

### Similar reports and how they fit

1. **HA peer restart and retained memory:** [K3s discussion 7337](https://github.com/k3s-io/k3s/discussions/7337) reports earlier-running servers growing from about 0.8 GB to 2–3 GB during peer restarts while the last-restarted server stays small. A maintainer suspected peer buffers and Go retaining memory after peers return, and cautioned that aggressive limits increase CPU and harm datastore/API performance. This resembles our startup order and memory spread, but it is an older report and does not establish the same cause here. The earlier emphasis on API watches alone was too narrow.
2. **Snapshot backlog rather than necessarily broken retry logic:** The [external-snapshotter v8.6.0 documentation](https://github.com/kubernetes-csi/external-snapshotter/blob/v8.6.0/README.md) documents exponential retries, worker concurrency, API QPS/burst, and separate sidecar/controller processing. The live CSI sidecar is v8.6.0 and has no explicit retry-interval override in its arguments. A five-minute maximum retry interval applies to each failed item; even 1,000 items retried every five minutes imply about 3.3 operations/s before accounting for multiple API calls per operation. Thus our 3.4 PATCH/s can be consistent with a large backlog, without proving an unusually tight retry-loop bug. The number of actively failing items is still unknown. Suspending only the hourly snapshot-creation CronJob would prevent new items but would not stop the CSI sidecar retrying existing contents.
3. **Go heap growth and reclamation:** The [Go GC guide](https://go.dev/doc/gc-guide) supports testing a lower `GOGC` or a `GOMEMLIMIT` soft budget to trade CPU for memory. The latter covers Go-managed runtime memory, not all host/process memory, and can be exceeded. An undersized budget can cause repeated collection and latency. Neither setting can eliminate objects still needed by etcd, watches, or controllers. Choose a budget above the measured live heap and runtime overhead, leave room for the OS/containerd, and monitor CPU and API/etcd latency. A hard systemd `MemoryMax` can kill the combined control plane when exceeded; it is unsuitable as the first experiment.

### Tuning claims checked against actual configuration

- At investigation time, master202's current-boot journal showed **etcd 3.5.21 with `snapshot-count=10000`** for the persistent `/var/lib/rancher/k3s/server/db/etcd` instance. Although [etcd 3.6's announcement](https://kubernetes.io/blog/2025/05/15/announcing-etcd-3.6/#memory) reports substantial memory savings, part comes from reducing the upstream default from 100,000 entries to 10,000. This cluster already uses 10,000; the published reduction cannot be applied as a predicted saving here. Further reductions trade retained Raft history against slow-follower catch-up and should require profile evidence, especially given prior disk contention. See [etcd maintenance guidance](https://etcd.io/docs/v3.5/op-guide/maintenance/#raft-log-retention).

## Research-based solution options

The following sources were checked after the leadership experiment. They inform candidate fixes but do not establish a specific upstream Kubernetes or LINSTOR defect matching this cluster.

- Kubernetes v1.31.14's garbage collector creates a monitor/informer for each discovered resource type and maintains a UID-based dependency graph from observed objects. This is compatible with the leader-only LINSTOR watch series and with memory increasing with many CR objects ([v1.31.14 GraphBuilder](https://github.com/kubernetes/kubernetes/blob/v1.31.14/pkg/controller/garbagecollector/graph_builder.go#L2491-L2574), [graph processing](https://github.com/kubernetes/kubernetes/blob/v1.31.14/pkg/controller/garbagecollector/graph_builder.go#L3059-L3068)). A separate 2026 kcp scale report measured garbage collection at about 12% of peak memory in its 10,000-workspace test and describes one monitor per resource type; kcp multiplied controllers per logical workspace, unlike this single-cluster K3s deployment, so this is supporting mechanism evidence, not a directly comparable estimate ([kcp load-test report](https://docs.kcp.io/kcp/main/developers/investigations/loadtest-report-sep-2026/#one-of-our-biggest-culprits-was-kubernetes-garbage-collection)).
- Kubernetes documentation advises against using custom resources as general application-data storage at very large object counts, while LINSTOR intentionally supports a Kubernetes CRD database backend. Therefore the object inventory is a plausible scaling pressure point, but that general guidance does not mean LINSTOR's supported backend is misconfigured ([Kubernetes custom-resource guidance](https://kubernetes.io/docs/concepts/extend-kubernetes/api-extension/custom-resources/#should-i-use-a-custom-resource-or-a-configmap)).
- **Preferred remediation path:** first inventory LINSTOR object counts, serialized sizes, owner references, and stale/orphan candidates by resource type. Reduce state only through LINSTOR-supported operations after confirming an object is obsolete; do not bulk-delete CR instances directly because they are the LINSTOR database. LINBIT documents the CRD backup/restore process and LINSTOR supports SQL backends including PostgreSQL/MariaDB. If object cleanup is insufficient, evaluate moving LINSTOR persistence off the Kubernetes API with LINBIT/Piraeus guidance, a verified export/import procedure, and a tested rollback/backup plan ([LINSTOR database backends](https://linbit.com/drbd-user-guide/linstor-guide-1_0-cn/#s-kubernetes-backend), [LINSTOR database backup/restore guidance](https://kb.linbit.com/linstor/kubernetes/linstor-kubernetes-upgrading-a-deployment-with-many-resources/)). No supported reverse-migration procedure for this exact deployed operator/version has yet been verified.
- **Controlled diagnostic only:** test a matching `enable-garbage-collector=false` configuration in a disposable, production-sized reproduction and measure K3s RSS, heap, object count, and watches. Kubernetes documents GC as enabled by default and requires the API server and controller-manager settings to agree; disabling it in production can prevent owner-reference cascading deletion and leave dependents behind, so it is not a recommended permanent fix ([kube-controller-manager flags](https://kubernetes.io/docs/reference/command-line-tools-reference/kube-controller-manager/)). Existing Kind testing measured API-server growth from synthetic LINSTOR objects but did not A/B-test K3s memory with GC enabled versus disabled.
- **Watch-cache tuning is limited:** Kubernetes documents `--watch-cache-sizes` as applying to built-in API resources, not CRDs. A per-LINSTOR-CRD cache-size setting is therefore not a supported fix. A global watch-cache disablement would affect API-server performance and should only be tested in a representative disposable cluster before considering any live change ([kube-apiserver flags](https://kubernetes.io/docs/reference/command-line-tools-reference/kube-apiserver/)).
- **Capacity/architecture fallback:** keep enough RAM on whichever master leads `kube-controller-manager` to tolerate the measured high state plus OS and etcd headroom; the 9.80 GB sample means 9 GB is already below the observed K3s RSS alone. K3s supports dedicated etcd-only and control-plane-only server roles, but that separates etcd from control-plane nodes; it does not split the embedded API server and controller-manager into separate memory domains ([K3s server roles](https://docs.k3s.io/installation/server-roles)). Treat this as containment, not a fix for the LINSTOR-associated growth.
- **Recommended order:** (1) measure per-resource counts/bytes and stale LINSTOR state, (2) run the GC on/off A/B in an isolated replica using the same Kubernetes/K3s and LINSTOR versions and representative object inventory, (3) if GC graph/object count is material, validate LINSTOR cleanup or an off-API database backend with vendor-supported migration and rollback, and (4) size master VMs to measured worst-case until the cause is reduced. Keep the current production GC and watch-cache settings unchanged during those diagnostic steps.
