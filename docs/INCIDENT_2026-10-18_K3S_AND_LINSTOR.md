# Incident: Kubernetes API timeouts and LINSTOR storage outage

**Date:** 2026-10-18  
**Status:** Unresolved; etcd has no stable leader and the Kubernetes API remains unavailable. The two affected DRBD resources were resumed, but application and snapshot integrity have not been verified.
**Data handling:** No etcd reset, datastore restore, or persistent-volume deletion was performed. Log files and archived journal entries were cleaned only; DRBD I/O was resumed after confirming all replicas were UpToDate. No data loss was observed, but application-level integrity has not been independently verified.

## Symptoms

- Requests to the Kubernetes API from the jumphost timed out or returned `ServiceUnavailable`.
- Master logs showed etcd peer TLS handshake timeouts, failed linearizable `ReadIndex` calls, `etcdserver: no leader`, and API handler deadlines. A node lookup stalled for about 10 seconds waiting for raft agreement.
- At 21:16 CEST, API readiness on 201 was refused and requests to 202 and 203 timed out. K3s on 201 was still activating with three restarts; 202 had also reached three restarts, and SSH to 203 stalled before its banner. The cluster was not stable at the last check.
- Later checks briefly showed `/readyz` succeeding on 201 and all seven nodes `Ready`, but this did not persist. By 21:38 CEST, 201 had reached 11 K3s restarts, 202 had one restart since its reset, SSH to 203 was timing out, and an etcd metrics sample on 202 showed `has_leader=0`. API requests hung again.
- At 21:41 CEST, 201's K3s process was running but its etcd metrics reported `has_leader=0`; SSH banner exchange timed out on both 202 and 203. Proxmox still showed all three VMs running. Their boot-disk read IOPS limits were active, with QEMU reads around 160–200 MB/s per VM and host NVMe utilization around 47%. The limits contain the high read bursts but have not restored etcd quorum or API service.
- At 21:42 CEST, API requests from 201 continued timing out; SSH to 202 and 203 also timed out. All master VMs remained running on Proxmox, with the configured read limits still present and host NVMe utilization around 41%. The latest guest root-space check on 201 showed 9.5 GiB free (57% used); `logrotate.timer` was active on 201 and reachable workers 204–206 and node119. Worker204 remained severely loaded (load average ~194), consistent with the previously observed DRBD blocked I/O.
- At 21:53 CEST, 201 still had no etcd leader and SSH to 202/203 timed out before receiving the SSH server banner. Pings and TCP connects to both masters' ports 22 and 2380 succeeded from Proxmox, so the timeout is not a basic IP reachability failure. All worker K3s agents were active and logrotate timers active. Thread-level checks showed 195 tasks in `D` state on 204 and 130 on 206; 204 had three blocked `dumpe2fs -h /dev/drbd1147` processes and Prowlarr threads, while 206 had three blocked `dumpe2fs -h /dev/drbd1136` processes and Radarr/.NET threads waiting in `percpu_rwsem_wait`. Worker206 I/O pressure remained elevated (PSI `some avg10` 10.43%, `full avg10` 7.13%); 204 PSI had subsided despite its high load average. Master201 logs still showed repeated 500 ms `ReadIndex` retries while K3s remained running.
- At 21:56 CEST, after resuming the two DRBD resources described below, thread-level `D` state dropped to zero on workers204–206. The volumes remained resumed and in sync on all three replicas. K3s agents and logrotate timers were active on those workers. The controller container was running on node119, but its recent log showed repeated inability to retrieve the LINSTOR leader-election lock because etcd requests timed out. Master201 still had `has_leader=0`, API requests timed out, and SSH to 202/203 still timed out before the server banner.
- At 21:59 CEST, the control-plane state was unchanged: K3s on 201 was running with 11 restarts, but its etcd metrics still showed `has_leader=0` and the local readiness request produced no timely response; SSH to 202 and 203 still timed out during banner exchange. Worker204 and 205 remained K3s-agent active with zero D-state threads; worker206 had also shown zero D-state threads after I/O resumed. Thus resuming the two DRBD volumes recovered the observed worker I/O stall but did not recover etcd/API quorum.
- At 22:17 CEST, authenticated `/readyz?verbose` on master201 still failed both `etcd` and `etcd-readiness`. SSH to masters202 and 203 continued timing out during banner exchange.

## Findings

1. **Log growth and disk pressure:** Master 201's root filesystem had previously reached 100% use. Its syslog and rotated syslog files had grown to multiple GiB, and etcd defragmentation failed with `no space left on device`. Log cleanup restored space; the most recent reading on 201 was 9.7 GiB free (56% used). Masters 202 and 203 also had multi-GiB syslog files, which were truncated, and archived journals were vacuumed.
2. **Control-plane instability:** The three masters repeatedly lost etcd peer connectivity during this investigation. Proxmox reboots temporarily brought API endpoints back, and one snapshot showed all seven Kubernetes nodes Ready with fresh leases and all three `/readyz` endpoints returning `ok`. That state did not persist; subsequent etcd readiness and API requests failed again.
3. **LINSTOR/DRBD outage:** The LINSTOR controller had been in `CrashLoopBackOff` with 246 restarts; the LINSTOR CSI controller had 1,447 restarts and multiple containers in `CrashLoopBackOff`. The `linstor-controller` service had no endpoints, and all four `LinstorSatellite` objects reported `Connected=False`. The previous controller log ended with `Database initialization error` (report `6AD519AD-00000-000000`, exit status 20). The available container log did not expose the underlying database error. At 21:56 CEST, the controller container was running, but direct container logs showed it repeatedly failing to retrieve the Kubernetes leader-election lock because etcd requests timed out; the service is still not verified ready.
4. **Worker I/O stalls:** Worker 204 had load average near 193 and high I/O pressure; 200 DRBD kernel threads were in uninterruptible `D` state. A sampled DRBD receiver stack was waiting in `drbd_flush_after_epoch`/`receive_Barrier`, and `dumpe2fs -h /dev/drbd1147` was blocked in `blkdev_fsync`. Worker 206 had load average near 130, 130 `D`-state threads, and high I/O pressure; a sampled thread was waiting in `jbd2` for DRBD volume `drbd1138`. These observations establish blocked DRBD I/O, but do not establish the original cause of the etcd failures.
5. **Workload impact:** The API listed failing or unhealthy pods, including the LINSTOR controller/CSI pods and application pods. A Ready node status alone did not indicate that storage-backed workloads were healthy.
6. **Shared Proxmox storage pressure:** The masters' 24 GiB boot disks reside on LVM storage `Kubernetes` on the same Samsung 990 PRO NVMe. The SSD reported no media/data-integrity errors, and the storage pool was about 87% full. Proxmox samples correlated NVMe saturation (about 98–100%) and 1.6–2.1 GB/s read bursts with individual master QEMU processes. Etcd explicitly logged leaders missing 500 ms heartbeats and attributing the delay to slow disk; API linearizable reads stalled for multiple seconds. The read storm moved between 202 and 203 during startup/catch-up. This is strong evidence of disk-contention contribution, though the guest operation causing repeated large reads is not identified.
7. **Peer TLS diagnosis remains unresolved:** All three `peer-ca.crt` files have the same SHA256 (`6cced225…f648ef49`), and each local `peer-server-client.crt` verifies against that CA. Direct mutual-TLS `openssl s_client` handshakes between 201 and 203 succeeded both ways. Nevertheless, etcd corruption-check requests logged `x509: certificate signed by unknown authority`, and servers logged peer connections rejected as `bad certificate`. The peer leaf certificates have different generation dates (201: Aug 4; 202/203: Jun 5, 2026), but their issuers and CA match. Certificate rotation was not attempted.
8. **Ubuntu MOTD fsck probe on CSI volumes:** On workers204 and 206, the blocked `dumpe2fs` processes had parents running `/usr/lib/update-notifier/update-motd-fsck-at-reboot`, invoked by `/etc/update-motd.d/98-fsck-at-reboot`. That Ubuntu script runs `dumpe2fs` across all mounted ext2/3/4 filesystems, including CSI ext4 mounts backed by DRBD. It repeatedly stalled on `/dev/drbd1147` (PVC `pvc-d7bc9b05-3f0b-4720-82f4-33d493646f42`) on 204 and `/dev/drbd1136` (PVC `pvc-3f238dd2-2f65-4fa9-b0d2-94e74dfdde5b`) on 206. This explains the extra blocked login/fsck probes; it does not explain the user suspension that blocked DRBD I/O. A DRBD-aware MOTD wrapper that skips the probe while any `/dev/drbd*` filesystem is mounted was deployed on workers204–206 and GPU node119. It preserves the standard fsck notice on nodes without DRBD mounts. After the volumes were resumed, D-state threads dropped to zero.
9. **The two user-suspended volumes were stuck during failed CSI snapshots:** On 204, 205, and 206, kernel logs show `susp-io(no -> user)` for the Prowlarr resource at 04:33:54–55 CEST and for Radarr at 04:34:06–07. The LINSTOR CSI driver log at 04:34:06 says the Prowlarr snapshot was registered, then `lvcreate` failed on node205 (and reported a failure on node204) because `VG linstor_vg` metadata was 521,660 bytes, above its maximum of 521,472 bytes. The same request reports I/O suspended on all three replicas. The Radarr snapshot request was cancelled immediately after its replicas were suspended. No matching resume transition for either resource appears before 21:55, when `drbdsetup resume-io` was run on all replicas. This identifies the direct cause of the persistent DRBD stalls: snapshot creation failed after suspension and left the user-suspend state set.
10. **LINSTOR VG metadata is exhausted on all three storage workers:** Current LVM reports show a 1,044,480-byte metadata area with 0 bytes free on 204 and 206, and only 512 bytes free on 205. The VGs contain 1,158–1,179 LVs, including 201–265 snapshot LVs and 746–790 backup LVs. Thin-pool data usage is 70.76% on 204, 77.50% on 205, and 89.79% on 206; thin-pool metadata usage is 5.36%, 5.53%, and 6.20%. The snapshot error is specifically the VG metadata area, not exhaustion of thin-pool metadata. The Flux snapshot reconciler runs hourly, prunes old `VolumeSnapshot` objects, and uses a class with `deletionPolicy: Retain`; retained backend snapshots may therefore outlive the Kubernetes objects. That policy interaction is a likely source of LV accumulation, but the remaining `VolumeSnapshotContent` and LINSTOR snapshot inventory must be compared after API recovery before calling it confirmed. The Ansible role installs the thin-pool autoextend profile on the hosts, but the CSI satellite container on 204 has no `/etc/lvm/profile` directory, matching the missing-profile warnings in the snapshot error. This is a separate autoextend configuration gap; it is not the reported VG metadata write failure.
11. **The etcd failure remains a separate unresolved problem:** At 22:07 CEST, master201 was still retrying linearizable `ReadIndex` calls and starting elections at term 781. TCP sessions to peers on port 2380 existed, but there was no leader. Proxmox RRD showed sustained reads from 202 and 203 (about 150–170 MB/s in recent minute averages, with day peaks around 2.1 and 1.9 GB/s), while 201 was near idle. The IOPS limits are present in the live QEMU command; current host NVMe latency/utilization were low after containment, and no scheduled Proxmox `vzdump` jobs are configured. SSH to 202 and 203 still times out during banner exchange. Their Proxmox configs have no QEMU guest agent or serial device, so the guest processes causing the reads cannot currently be inspected. The read bursts are a plausible contributor to the original quorum loss, but their guest-side source and causal link to etcd timeouts remain unproven.

The DRBD stalls are explained by failed snapshots against an exhausted LINSTOR VG metadata area. Their relationship to the etcd peer timeouts is not proven. Stable etcd quorum, recovery of the LINSTOR controller, and application/snapshot integrity checks remain outstanding.

## Recovery actions taken

- Cleaned oversized syslog files and vacuumed archived systemd journal entries; no application logs or persistent-volume data were deleted.
- Applied the Kubernetes node log-rotation setup on masters 201–203. The change is in commits `4cad743`, `eed12a7`, and `ded72d7`.
- Rebooted master 201 through Proxmox. Graceful reboot of 202 timed out, so it was hard-reset and started again. Graceful reboot of 203 timed out, so it was hard-reset. A later hard reset of 201 restored SSH and briefly restored API readiness. No etcd reset/restore command was run.
- Later, Proxmox root SSH access from the jumphost was used to identify VM 202 as a read-burst source (~1.6–1.75 GB/s). Its graceful shutdown again timed out; only VM 202 was reset. Its QEMU read rate fell to zero, but a similar read burst then moved to VM 203. Proxmox read limits of `iops_rd=2500` were applied to the `scsi0` boot disks of VMs 201, 202, and 203. This reduced the 203 observed read rate from ~1.6 GB/s to ~200 MB/s and NVMe utilization from ~100% to ~28% in one sample. Subsequent samples still showed renewed K3s restarts, loss of etcd leader, and API timeouts, so this is a temporary containment measure rather than recovery.
- Deployed an Ansible-managed wrapper for `/etc/update-motd.d/98-fsck-at-reboot` on storage workers204–206 and GPU node119. The wrapper skips Ubuntu's all-mounted-ext-filesystem scan when DRBD devices are mounted, avoiding repeated `dumpe2fs` probes that can hang in the storage path. This suppresses the secondary MOTD-triggered probes; it does not repair DRBD or restore quorum.
- Used `drbdsetup resume-io` on all three replicas for minors 1147 and 1136 after confirming all replicas were UpToDate, quorum-enabled, connected, with no in-flight or out-of-sync blocks. Follow-up showed both resources resumed and all worker thread-level D-state counts at zero. No repair/resync was triggered.
- A later API snapshot from 201 showed all seven nodes Ready, but LINSTOR controller, affinity controller, CSI controller, and Piraeus operator remained in `CrashLoopBackOff`; all four satellites were `Connected=False`. Controller log retrieval through the Kubernetes API then failed because the node proxy to 192.168.1.119:10250 returned 502. No controller diagnostic helper was deployed, and no LINSTOR/DRBD or etcd data was changed.
- Subsequent API requests from 201 hung with `context deadline exceeded`. A read-only attempt to inspect the LINSTOR controller log volume directly on `.119` was denied by host permissions; its SSH account requires an interactive sudo password. Proxmox serial terminal opens but yields no guest shell. No helper pod could be created while the API was timing out.
- API readiness and all-node Ready status were observed temporarily, but follow-up checks showed renewed etcd readiness failures and API timeouts.

## Follow-up

- Restore stable etcd quorum and verify `/readyz` and node leases across all masters over a sustained period.
- After API recovery, inspect the failed Prowlarr/Radarr `VolumeSnapshot` and `VolumeSnapshotContent` objects, compare retained LINSTOR snapshots and backup LVs to the intended retention policy, and verify application data before any cleanup.
- Resolve the LINSTOR VG metadata capacity/retention issue and make snapshot failure cleanup reliably resume DRBD I/O. The metadata area is effectively exhausted on all three storage workers; do not remove retained snapshots until their ownership and recovery value are confirmed.
- Identify LINSTOR/PVC ownership and replica health for `pvc-d7bc9b05-3f0b-4720-82f4-33d493646f42` (204) and `pvc-3f238dd2-2f65-4fa9-b0d2-94e74dfdde5b` (206) once the API/controller is available; verify data integrity before filesystem repair or workload restart.
- Restore quorum using surviving persistent member state and its existing snapshots. Do not run a force-new-cluster, etcd reset/restore, or member removal until authoritative member history and the last committed revision are established.
- Identify why master startup/catch-up generates very high reads on the shared NVMe; review Proxmox/KVM and guest block I/O traces before changing VM disk limits. The 2500 read IOPS limits are active runtime configuration and may constrain future catch-up; remove or adjust them after the source is understood and the cluster is stable.
- Restore a guest diagnostic path for masters 202 and 203 (SSH, QEMU guest agent, or serial console) so the read-heavy process can be identified; do not infer it from Proxmox block counters alone.
- Diagnose the transient etcd peer TLS verification failures and confirm the authoritative member/peer identity before any certificate changes.
- Obtain the detailed LINSTOR report for `6AD519AD-00000-000000`; restore controller database access before attempting changes to LINSTOR resources or DRBD volumes.
- Reconnect the LINSTOR satellites and verify DRBD resource state and persistent-volume integrity before considering worker reboots.
- Re-run the Ansible hygiene playbook on every target node after connectivity is stable. The previous run timed out waiting for privilege escalation on worker 204.
